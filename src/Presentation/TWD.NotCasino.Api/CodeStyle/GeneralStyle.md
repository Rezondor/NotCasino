# Общий стиль кода в C# проектах

## Общие правила

1. Использовать единый стиль во всех модулях проекта.  
2. Код должен быть **читаемым, предсказуемым и единообразным**.  
3. Следовать принципам как минимум KISS и DRY.  
4. Все классы и методы должны быть асинхронными, если они работают с внешними источниками (БД, файлы, сети).  

---

## Именование

### Переменные и поля
- Использовать только `var` при объявлении переменных, если тип очевиден из правой части выражения.  
- Для приватных полей использовать `_camelCase`.  
- Константы оформлять в `UPPER_SNAKE_CASE`.  

### Методы и функции
- Наименование в стиле `UpperCamelCase`.  
- Название должно отражать действие или возвращаемое значение.  
- Методы, возвращающие `bool`, должны начинаться с `Is`, `Has`, `Can`, `Should`.

### Классы и интерфейсы
- Каждый класс в отдельном файле.  
- Наименование классов должно отражать их суть и назначение.  
- Интерфейсы начинаются с буквы `I` (например, `IRepository`).  
- Исключения должны оканчиваться на `Exception`.  
- DTO-объекты заканчиваются на `Dto`, запросы и команды — `Request` и `Command`.

---

## Стиль кода

### Скобки и отступы
- Для однострочных `if`, `else`, `for`, `foreach`, `while` допускается отсутствие фигурных скобок.  
- Для многострочных конструкций скобки обязательны.  
- Отступ — 4 пробела.  

### Пробелы
- Пробел после ключевых слов: `if (condition)`, `while (true)`  
- Пробелы вокруг операторов: `a + b`, `x == y`  
- Не использовать лишние пустые строки.  

### Using
- Все `using` должны быть упорядочены и сгруппированы:  
  1. Системные (`System.*`)  
  2. Внешние библиотеки  
  3. Внутренние проекты  
- Использовать директиву `using` внутри файла, а не глобальные импорты без необходимости.  

---

## Методы и функции

1. Методы должны быть короткими и решать одну задачу.  
2. Асинхронные методы должны иметь суффикс `Async`.  
3. Обязательна проверка входных параметров на `null` или недопустимые значения.  

---

## Работа с исключениями

1. Исключения должны использоваться только для действительно исключительных ситуаций.  
2. Логировать все необработанные исключения.  
3. Не использовать пустые `catch`.  
4. Если исключение перехватывается и выбрасывается повторно — использовать `throw;`, а не `throw ex;`.  

---

## Документирование

1. Публичные методы и классы должны иметь XML-комментарии.  
2. Для сложной логики — использовать комментарии внутри метода.  
3. Комментарий должен объяснять «зачем», а не «что делает строка кода».  

---

## Итоговые правила

1. Переменные объявлять через `var`.  
2. Методы именовать в стиле `UpperCamelCase`.  
3. Каждый класс в отдельном файле.  
4. Однострочные `if` можно писать без скобок.  
5. Названия классов должны отражать их суть.  
6. Асинхронные методы оканчиваются на `Async`.  
7. Обязательная обработка ошибок.  
8. Следовать единым правилам оформления кода для всей команды.
